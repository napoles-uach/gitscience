# LLM-assisted formalization

GitScience separates formalization into three authorities:

```text
LLM proposes an obligation and semantic mapping
                    |
                    v
human approves the intended mathematical statement
                    |
                    v
Lean checks a trusted proof contract
```

The LLM is neither the semantic authority nor the proof checker. Lean establishes
only the approved deductive statement. GitScience continues to expose assumptions,
unformalized content, and the scientific grounding between the theorem, model, and
physical system.

## Agent request

An installed formalization agent receives the deterministic canonical claim state
and a catalog of trusted formal proof contracts:

```bash
gitscience formal inspect GS-QT-0003
gitscience formal request GS-QT-0003 \
  --with physics_intern \
  --model YOUR_PHYSICS_INTERN_MODEL
```

The command creates an `FM-*` draft. It does not execute Lean and cannot affect
claim status. The proposal records:

- a Lean theorem signature without a proof body;
- a source-to-formal semantic mapping;
- explicit mathematical assumptions;
- scientific content left outside Lean;
- a grounding status (`unlinked`, `partial`, or `established`);
- an optional statement and verification contract copied exactly from one
  installed trusted-verifier catalog entry.

GitScience does not execute arbitrary Lean source generated by an LLM. It also
rejects a statement that attempts to reuse an unrelated trusted proof contract.
A proposal without an exact trusted statement-contract pair remains a useful open
formalization obligation.

## Human semantic approval

Inspect and commit the draft before approving it:

```bash
gitscience formal show FM-000001
gitscience commit -m "Propose formal transport obligation"
gitscience formal approve FM-000001
gitscience commit -m "Approve formal transport semantics"
```

Approval records the Git identity and locks the formal statement by SHA-256. A
changed statement invalidates the approval and any current proof evidence. Changing
the theorem therefore requires a visible new revision and another approval.

## Trusted Lean verification

Only an approved and committed request can invoke its selected verifier:

```bash
gitscience formal verify FM-000001
gitscience commit -m "Record Lean evidence for FM-000001"
gitscience claim explain GS-QT-0003
```

The evidence references the exact claim and formalization revisions. A successful
Lean run sets the logical dimension to `proven`. If scientific grounding remains
partial, the derived status remains `conditional_proven` and the grounding gap is
an open obligation.

## Trust boundary

The three dimensions answer different questions:

| Dimension | Question |
| --- | --- |
| `formalization` | Did a human accept that the theorem represents the intended claim? |
| `logical` | Did Lean establish the approved theorem under its premises? |
| `scientific_grounding` | Are the theorem's objects and premises connected to the implemented model and physical interpretation? |

A compiled Lean file cannot by itself promote `scientific_grounding` from partial
to established.
